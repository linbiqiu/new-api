# 用户总量限制、中文额度提示与用量提醒设计

> 日期：2026-08-06
> 状态：设计已确认，待用户审阅书面规格
> Canonical spec：本文件
> 关联现有设计：`docs/superpowers/specs/2026-06-26-model-quota-limit-design.md`

## 1. 背景

现有“模型额度规则”支持按用户分组、个人用户和订阅计划，为指定模型或模型前缀设置金额额度限制。当前存在三个不足：

1. 规则必须选择具体模型，不能限制某用户跨全部模型的总金额或总 Token。
2. 钱包、订阅、API 令牌和模型额度不足时，部分接口向用户返回英文技术错误或内部 quota 数值。
3. 系统缺少按当天 Token 里程碑及订阅周期使用率主动提醒用户的能力。

## 2. 目标

1. 在现有分组、用户、订阅计划三类规则中增加“全部模型”限制范围。
2. 全部模型规则可单独或同时限制总金额与总 Token。
3. 所有限制最终按用户独立核算，不建立分组或套餐共享池。
4. 保留并叠加现有指定模型规则，任一命中规则达到上限即拒绝请求。
5. 将额度与计费相关错误统一为始终中文、可操作、OpenAI 结构兼容的响应。
6. 用户当天 Token 达到 100M 及之后每个 100M 档位时发送用量提醒。
7. 每个订阅在当前额度周期首次达到 80% 使用率时发送一次提醒。
8. 飞书通知采用已确认的“方案 B：温和摘要”卡片样式。

## 3. 非目标

1. 不实现分组成员或套餐用户共享额度池。
2. 不对上游模型错误、请求参数错误和鉴权错误做全局文案改写。
3. 不在达到 Token 上限时中断正在生成的流式响应。
4. 不新增自定义周期；沿用每日、每周、每月、永久累计和订阅额度周期。
5. 不重构为通用策略 DSL 或策略引擎。
6. 不在本工作项中执行生产发布、镜像构建或部署。

## 4. 已确认的业务规则

### 4.1 核算对象

- 分组规则：组内每个用户分别拥有一份计数器。
- 用户规则：指定用户拥有一份计数器。
- 订阅计划规则：每个用户、每个实际计费订阅实例分别拥有一份计数器。
- 不同用户之间不共享金额或 Token 上限。

### 4.2 Token 口径

- Token 用量采用系统用量日志一致的口径：`输入 Token + 输出 Token`。
- 后端存储整数 Token；前端输入和展示单位为 `M Token`。
- `1M = 1,000,000 Token`，`100M = 1 亿 Token`。
- 前端允许最多三位小数，例如 `1.25M = 1,250,000 Token`。
- 图片、视频等没有标准 Token 的请求只累计实际金额，不累计 Token。

### 4.3 周期

- 分组和用户规则支持：`daily`、`weekly`、`monthly`、`total`。
- 订阅计划规则跟随实际计费订阅的当前额度周期。
- 每日周期使用北京时间当日 00:00 至次日 00:00。
- 每周周期使用北京时间周一 00:00 至下周一 00:00。
- 每月周期使用北京时间每月 1 日 00:00 至下月 1 日 00:00。
- `total` 为永久累计，除非管理员手动重置。
- 所有时间边界统一使用 `Asia/Shanghai`，不依赖服务器本地时区。

### 4.4 叠加规则

用户请求可能同时命中分组、个人用户、实际计费订阅计划和指定模型规则。所有命中规则取交集：

- 任一金额上限达到或预计本次请求将超过上限，拒绝请求。
- 任一 Token 上限已达到，拒绝请求。
- 金额与 Token 同时配置时，任一指标达到上限即拒绝。
- 规则来源优先级只用于诊断展示，不用于覆盖其他规则。

### 4.5 Token 实用上限

输出 Token 只能在请求结束后确定，因此采用“实用上限”：

- 请求开始时，若当前 Token 已用量达到上限，则拒绝。
- 未达到上限时允许请求，完成后按真实 Token 累计。
- 最后一个请求或多个并发在途请求可能使实际用量略微超过上限。
- 超过后所有新请求立即被拒绝。

不使用 `max_tokens` 预占，也不中断已经开始的生成。

## 5. 方案选择

采用“扩展现有额度规则体系”，不新增一套平行的总量限制模块：

- 复用现有分组、用户、订阅计划规则表和管理 API。
- 复用现有周期计算、用户用量记录、Redis 缓存和管理员页面。
- 历史规则迁移后标记为指定模型规则，额度数据保持不变。
- 页面显示名称由“模型额度规则”调整为“用量限制规则”；保留现有路由和 API 路径，避免书签与客户端失效。

## 6. 数据模型

### 6.1 规则表扩展

以下三张表增加相同字段：

- `model_quota_group_rules`
- `model_quota_user_rules`
- `model_quota_plan_rules`

新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `scope` | varchar(16) | `model` 或 `all`；历史记录迁移为 `model` |
| `token_limit` | bigint | 整数 Token 上限，`0` 表示不限制 |

现有 `quota_limit` 继续使用内部整数 quota 单位：

- `scope=model`：保留当前指定模型金额限制，`quota_limit` 必须大于 0，`token_limit` 第一版固定为 0。
- `scope=all`：`model_pattern` 为空，`match_mode` 被忽略；`quota_limit` 和 `token_limit` 至少一项大于 0。
- 金额输入、展示和错误响应统一按系统人民币换算能力处理，不直接暴露内部 quota。

### 6.2 规则使用记录扩展

`user_model_quota_usage` 增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `token_limit` | bigint | 当前规则的 Token 上限快照 |
| `token_used` | bigint | 当前周期实际 Token 累计 |

现有金额字段 `quota_limit`、`quota_used` 保持不变。所有增量必须非负并使用原子更新。

使用记录唯一身份至少包含：用户、规则来源、规则 ID、订阅实例 ID和周期边界。实现应使用数据库唯一约束处理并发懒创建，不能依赖“先查询再创建”保证唯一性。

### 6.3 每日用户用量计数器

新增 `user_daily_usage_counters`，独立于是否存在额度规则，用于每日里程碑提醒：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | 由 GORM 生成 |
| `user_id` | int | 用户 ID |
| `usage_date` | varchar(10) | 北京时间日期 `YYYY-MM-DD` |
| `token_used` | bigint | 当日输入与输出 Token 总量 |
| `quota_used` | bigint | 当日实际消费 quota |
| `created_at` | bigint | 创建时间 |
| `updated_at` | bigint | 更新时间 |

`(user_id, usage_date)` 建立唯一索引。更新使用原子增量，不在每次请求后扫描消费日志。

### 6.4 通知事件与 Outbox

新增 `user_notification_events` 作为持久化通知 outbox：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | |
| `user_id` | int | 接收用户 |
| `event_type` | varchar(32) | `daily_token_milestone` / `subscription_usage_80` |
| `event_key` | varchar(128) | 幂等键 |
| `payload` | text | 通知所需结构化数据，使用 `common.Marshal` / `common.Unmarshal` |
| `status` | varchar(16) | `pending` / `sending` / `sent` / `failed` |
| `attempts` | int | 发送尝试次数 |
| `next_retry_at` | bigint | 下次可重试时间 |
| `lease_until` | bigint | 多节点发送租约 |
| `sent_at` | bigint | 成功发送时间 |
| `created_at` | bigint | |
| `updated_at` | bigint | |

`(user_id, event_type, event_key)` 建立唯一索引：

- 每日里程碑键：`YYYY-MM-DD:<milestone_m>`。
- 订阅 80% 键：`<subscription_id>:<period_start>:80`。
- 多节点工作器使用状态条件更新和租约领取事件。
- 发送失败按退避策略重试；达到最大次数后保留 `failed` 状态供管理员排查。

所有新增表和索引必须兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。

## 7. 规则生命周期

### 7.1 创建与更新

- 创建全部模型规则时，金额与 Token 至少填写一项。
- 只修改金额或 Token 上限：更新现有 active 使用记录的限额快照，保留已用量。
- 调低限额至小于当前已用量：下一次请求立即拒绝。
- 修改对象、范围、模型匹配或周期：将旧使用记录归档，新规则从零开始计数。
- 禁用规则：立即停止匹配，历史使用记录保留。
- 删除规则：停止匹配并保留历史记录；不能物理删除审计数据。

### 7.2 重置

- 管理员手动重置一条使用记录时，同时清零金额和 Token。
- 重置必须记录管理员操作日志。
- 订阅管理员重置会形成新的有效额度周期标识，使订阅 80% 提醒可在新周期再次触发。

### 7.3 审计

以下操作记录管理员 ID、目标对象、旧值、新值、时间和请求 ID：

- 创建规则
- 修改规则
- 启用或禁用规则
- 删除规则
- 手动重置使用记录

## 8. 请求与结算数据流

### 8.1 请求前检查

1. 认证和分组分发完成后，解析用户与分组规则。
2. 对金额限制复用现有预估费用，检查 `已用 + 预估 > 上限`。
3. 对 Token 限制检查 `当前已用 >= 上限`。
4. 订阅计费完成资金来源选择后，将订阅计划规则绑定到实际选中的 `user_subscription_id` 和 `plan_id`；钱包计费请求不匹配订阅计划规则。
5. 任一规则失败时，回滚已经完成的预扣并返回中文错误，不调用上游。

第 4 条用于保证多个有效订阅及钱包回退场景下，计划规则不会错误绑定到“第一条活跃订阅”。历史指定模型计划规则也采用实际计费订阅关联，以保证同一规则体系语义一致。

### 8.2 请求后累计

仅在实际计费结算成功后累计：

- `quota_used += actual_quota`
- `token_used += prompt_tokens + completion_tokens`
- 每日计数器同步累计相同的实际金额和 Token。

同步文本、流式文本、音频、图片、视频和异步任务必须汇入同一个结算观察接口：

- 有 Token 用量的路径累计金额和 Token。
- 无标准 Token 的路径只累计金额。
- 上游失败且没有产生实际费用或 Token 的请求不累计。
- 退款不能产生负收费；计数器只记录最终实际消费，不能通过负增量制造可用额度。

计数器持久化更新同步完成，通知投递异步执行。计数器更新失败不能撤销已经完成的上游响应，但必须记录请求相关错误并进入异常审计；后续校验无法确认用量时执行 fail-closed。

### 8.3 故障策略

- Redis 不可用：回退数据库读取和原子更新。
- Redis 与数据库均无法完成规则或用量校验：返回 HTTP 503，不调用上游。
- 对外提示：`用量校验暂时不可用，请稍后重试。`
- 错误码：`usage_limit_check_unavailable`。
- 不使用当前模型额度中间件的 fail-open 行为。

## 9. 中文额度错误

### 9.1 返回契约

- 保持现有 OpenAI 兼容错误 JSON 结构。
- 保持额度不足类现有 HTTP 403，校验服务不可用使用 HTTP 503。
- 对外 `message` 始终为中文，不跟随用户语言设置。
- 使用稳定机器错误码，调用方不得依赖中文文案分支。
- 原始数据库错误、内部 quota 和英文技术信息只写入服务端日志。

### 9.2 错误目录

| 场景 | 错误码 | 中文消息模板 |
|---|---|---|
| 钱包已用完 | `wallet_quota_exhausted` | 当前账户余额已使用完毕，请充值后继续使用。 |
| 钱包不足以完成请求 | `wallet_quota_insufficient` | 当前账户余额不足以完成本次请求。当前余额 ¥{remaining}，本次预计需要 ¥{required}。 |
| 无有效订阅 | `subscription_unavailable` | 当前没有可用的订阅计划，请先开通或续费后再使用。 |
| 订阅已过期 | `subscription_expired` | 您的“{plan}”已到期，请续费后继续使用。 |
| 订阅额度已用完 | `subscription_period_quota_exhausted` | 您的“{plan}”本周期额度已使用完毕，将于 {reset_at} 重置。 |
| 订阅不足以完成请求 | `subscription_period_quota_insufficient` | 您的“{plan}”本周期剩余额度不足以完成本次请求。剩余 ¥{remaining}，预计需要 ¥{required}，将于 {reset_at} 重置。 |
| API 令牌额度已用完 | `api_token_quota_exhausted` | 当前 API 令牌额度已使用完毕，请更换令牌或联系管理员。 |
| API 令牌额度不足 | `api_token_quota_insufficient` | 当前 API 令牌剩余额度不足以完成本次请求，请更换令牌或联系管理员。 |
| 全部模型金额达到上限 | `all_models_amount_limit_exhausted` | 您{period}的全部模型金额额度已达到上限（¥{limit}），将于 {reset_at} 重置。 |
| 全部模型金额剩余不足 | `all_models_amount_limit_insufficient` | 您{period}的全部模型金额剩余额度不足以完成本次请求。剩余 ¥{remaining}，预计需要 ¥{required}，将于 {reset_at} 重置。 |
| 全部模型 Token 达到上限 | `all_models_token_limit_exhausted` | 您{period}的全部模型 Token 用量已达到上限（{limit_m}M），将于 {reset_at} 重置。 |
| 指定模型金额达到上限 | `model_amount_limit_exhausted` | 您{period}的“{model}”模型金额额度已达到上限（¥{limit}），将于 {reset_at} 重置。 |
| 指定模型金额剩余不足 | `model_amount_limit_insufficient` | 您{period}的“{model}”模型金额剩余额度不足以完成本次请求。剩余 ¥{remaining}，预计需要 ¥{required}，将于 {reset_at} 重置。 |
| 校验服务不可用 | `usage_limit_check_unavailable` | 用量校验暂时不可用，请稍后重试。 |

永久累计规则的消息不显示不存在的重置时间，改为提示联系管理员调整额度。订阅禁止钱包回退时只返回订阅额度消息，不暴露内部计费策略。

## 10. 通知设计

### 10.1 每日 Token 里程碑

- 对所有用户默认开启，与是否配置总量规则无关。
- 北京时间当日 Token 达到 `100M、200M、300M……` 时触发。
- 每个档位每天最多一次。
- 单次请求跨越多个新档位时，只创建最高档位通知，并通过事件状态将较低档位视为已覆盖。
- 后续达到下一档位时继续提醒。

通知内容：

- 当天累计 Token
- 当天实际消耗金额（人民币）
- 下一提醒档位
- 每个有效订阅的套餐名称、当前额度周期、已使用金额、剩余金额

多个订阅不得将不同周期的额度直接相加，必须逐项展示。

### 10.2 订阅 80% 提醒

- 每个订阅、每个额度周期首次达到 80% 使用率时提醒一次。
- 使用率计算：`amount_used / amount_total`。
- `amount_total = 0` 的无限额度订阅不触发。
- 续期、周期重置或管理员重置后，可在新周期再次触发。
- 升级现有订阅低额度提醒入口，不再并行发送旧的每日一次订阅预警，避免重复。

通知内容：

- 套餐名称
- 当前周期
- 已使用比例
- 本周期已使用金额
- 本周期剩余金额
- 重置时间

### 10.3 通知渠道

- `notify_type` 已明确设置：严格使用用户选择的邮件、Webhook、Bark、Gotify 或飞书应用。
- `notify_type` 未设置：默认使用飞书应用。
- 默认飞书无法送达（例如用户未绑定飞书）：回退到账户邮箱。
- 用户明确选择的渠道发送失败时不跨渠道回退，由 outbox 重试原渠道。
- 用户可关闭“每日 Token 用量提醒”，该设置对历史用户默认开启。
- 订阅 80% 提醒作为额度安全提醒保持开启。

`UserSetting` 增加可区分“未设置”和“显式关闭”的每日里程碑开关。`relaykit/` 中的 DTO 变更不得引入根模块依赖。

### 10.4 飞书方案 B 卡片

每日 Token 卡片采用温和摘要：

- 标题：`今日 Token 用量提醒`
- 副标题：`已达到 {milestone}M 档位`
- 摘要区：当天累计 Token、当天消耗金额、下一档位
- 订阅区：每个有效订阅一行显示已用和剩余金额

订阅额度卡片采用温和摘要：

- 标题：`订阅额度温馨提醒`
- 副标题：套餐名称
- 强调区：已使用比例和剩余金额
- 明细区：本周期累计使用及周期结束时间

卡片避免展示内部 quota、规则 ID、数据库字段和技术错误。

## 11. 管理端设计

### 11.1 页面

- 现有三个 Tab 保留：分组规则、订阅计划规则、用户规则。
- 菜单及页面标题改为“用量限制规则”。
- 保留现有 `/model-quota-rules` 前端路由。
- 列表新增：限制范围、金额上限、Token 上限、金额已用/剩余、Token 已用/剩余。

### 11.2 创建和编辑表单

- 限制范围使用分段控件：`全部模型` / `指定模型`。
- 选择全部模型时隐藏模型名称和匹配模式。
- 金额输入后缀为 `CNY`。
- Token 输入后缀为 `M Token`。
- 金额和 Token 至少填写一项。
- 同时填写时显示“任一上限达到都会停止请求”。
- 表单明确说明分组和套餐规则按每个用户独立核算。

### 11.3 使用详情

- 管理员用户用量详情同时显示金额和 Token 进度。
- 显示规则来源、限制范围、周期、重置时间和状态。
- 管理员可一并重置金额和 Token 使用量。

用户端新增独立用量面板不在本次范围内；用户通过现有日志、中文错误及主动提醒获得反馈。

## 12. API 兼容

继续使用现有 `/api/model-quota/*` 接口，在请求和响应中增加：

- `scope`
- `token_limit`
- `token_used`
- `token_remain`
- 金额与 Token 使用百分比

兼容规则：

- 未传 `scope` 的历史客户端按 `scope=model` 处理。
- 历史模型规则仍要求 `model_pattern` 和正数 `quota_limit`。
- 全部模型规则要求金额或 Token 至少一项为正数。
- API 接收和返回整数 Token；`M Token` 转换只发生在前端。

## 13. 可观测性

### 13.1 日志

以下异常使用带请求 ID、用户 ID、规则 ID 和订阅 ID 的结构化日志：

- 规则读取失败
- 计数器读取或原子更新失败
- Redis 回退数据库
- 通知事件创建冲突
- 通知发送失败和最终失败
- 实际使用量超过配置上限

日志不得包含 API 密钥、通知密钥或用户隐私内容。

### 13.2 指标

实施时必须增加：

- 用量限制拦截次数，按来源和指标分类
- Token 或金额实际超限幅度
- Redis 回退次数
- 用量校验 503 次数
- 通知事件 pending/sent/failed 数量
- 通知发送延迟和重试次数

## 14. 迁移与回滚

### 14.1 数据迁移

1. 为三张规则表添加 `scope` 和 `token_limit`。
2. 将历史规则 `scope` 设为 `model`，`token_limit` 设为 0。
3. 为使用记录添加 `token_limit` 和 `token_used`，历史值设为 0。
4. 创建每日计数器和通知 outbox 表及唯一索引。
5. 迁移必须可重复执行，并兼容三种数据库。

### 14.2 分阶段启用

1. 先部署兼容新字段但不开启新规则的后端。
2. 验证历史指定模型规则和计费链路。
3. 部署管理端并创建小范围测试规则。
4. 验证计数、中文错误和通知后再扩大使用范围。

### 14.3 回滚

- 应用回滚后历史指定模型规则仍可读取原字段。
- 新增列和表暂不删除，避免不可逆数据丢失。
- 回滚期间禁用 `scope=all` 规则和通知工作器。
- 已记录的使用量与通知事件保留供审计。

## 15. 测试策略

### 15.1 后端行为测试

1. 分组、用户、订阅计划创建全部模型金额规则。
2. 三类对象创建全部模型 Token 规则。
3. 金额和 Token 双上限取最严格结果。
4. 组内两个用户分别累计，互不影响。

13. Redis 故障回退数据库；数据库也失败时返回中文 503。

### 15.2 错误契约测试

- 不泄露内部 quota 或原始错误
- 金额为人民币格式

### 15.3 通知测试

11. 多节点并发只创建一个 outbox 事件。

## 16. 验收标准

1. 管理员无需选择具体模型即可按分组、用户或订阅计划设置全部模型总金额或总 Token 上限。
2. 所有限制按用户独立核算，且能与现有指定模型规则叠加。
3. 用户达到任一上限后，新请求收到准确、友好的中文提示。
4. 每日 Token 里程碑与订阅 80% 提醒按已确认的频率、渠道和卡片样式送达。
5. 历史指定模型规则、API 路径和客户端请求保持兼容。
6. 三种数据库兼容，计数和通知在并发、多节点及 Redis 故障场景下保持一致。
7. 所有新增计费乘数、quota 转换和累计路径遵守项目 billing safety invariants。

## 17. 已确认决策摘要

- 每个用户独立核算。
- Token 为输入加输出，界面单位 M。
- 沿用现有周期。
- 多规则全部生效，取最严格结果。
- Token 使用实用上限，不预占 `max_tokens`。
- 每日每 100M 提醒，跨多档只发最高档。
- 多订阅逐项展示。
- 订阅当前周期达到 80% 使用率时每周期提醒一次。
- 未设置通知渠道时默认飞书，无法送达回退邮箱。
- 用户显式设置通知渠道后严格使用该渠道。
- 飞书卡片采用方案 B。
- 额度与计费错误始终返回中文。
- 校验存储完全不可用时 fail-closed，返回中文 503。
